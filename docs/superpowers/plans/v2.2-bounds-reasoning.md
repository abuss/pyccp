# pyccp v2.2 Implementation Plan — Bounds-Based Reasoning

> **Status:** Draft (ready for implementation)
> **Date:** 2026-10-18
> **Goal:** Extend bounds reasoning to 4 propagators (NeqLinear, Multiply, Element, Cardinality)
> **Expected Outcome:** 5-15% speedup on N-Queens; maintain Send+More=Money baseline

## Overview

v2.1 introduced bounds tracking and bounds-based propagation for `LinearEq` and `LessThan`. v2.2 extends this pattern to the remaining propagators that currently operate only on domain enumeration with all-but-one-fixed ceilings.

**Architecture:** Bounds parallel domains; both must stay consistent. Domain pruning follows bounds tightening.

**Pattern:** See `LinearEq::compute_bounds()` and `LessThan` for the reference implementation in `rust/src/propagators.rs` lines 128-227.

## Task Breakdown

### Task 1: NeqLinear — Interval Propagation for Inequality (HIGH PRIORITY)

**Ceiling:** Currently detects `all-but-one-fixed` only; cannot prune when 2+ terms open.

**Upgrade:** Compute interval min/max for remaining terms. Prune values that would force sum == k.

**Example:**
```
x + y != 5 with x ∈ [2,3], y ∈ [2,3]
→ min_sum = 4, max_sum = 6
→ k = 5 is within [4,6], but not exactly one value forces it
→ No pruning (correct)

x + y != 5 with x ∈ [2,3], y ∈ [2]
→ min_sum = 4, max_sum = 5
→ k = 5 is max value; if x ∈ {3} and y ∈ {2}, sum = 5 → conflict
→ Prune x = 3 (forces equality, violates !=)
```

**Implementation:**

- **File:** `rust/src/propagators.rs`, NeqLinear impl (lines 15-40)
- **New method:** `compute_bounds_for_open(store, open_terms) -> (i64, i64)`
  - Compute min/max sum of open terms given fixed terms
  - Return `(min_sum, max_sum)`
- **Update propagate():**
  - Compute min/max for open terms (new method)
  - If `k` is within bounds but forcing a single value: analyze which term(s) must change
  - For single-value-forcing cases, prune the forcing value from the term's domain
- **Tests:**
  - `neq_linear_bounds_single_forcing` - one open term, k forces specific value
  - `neq_linear_bounds_range_ok` - k outside min/max, no conflict
  - `neq_linear_bounds_partial_open` - 2+ open terms, k within range, no single forcing

**Estimated LOC:** 30-40 (propagate logic + helper)

---

### Task 2: Multiply — Divisibility Bounds (MEDIUM PRIORITY)

**Ceiling:** Currently needs one side fixed; cannot reason about bounds-based divisibility.

**Upgrade:** When one side has bounds, compute possible divisors/quotients; prune impossible values.

**Example:**
```
x * y = 12 with x ∈ [3,5], y ∈ [1,10]
→ If x = 3, y = 4
→ If x = 4, y = 3
→ If x = 5, y ∉ divisors of 12 (no integer solution)
→ Prune y to {3,4} and x to {3,4}
```

**Implementation:**

- **File:** `rust/src/propagators.rs`, Multiply impl
- **New method:** `divisors_of(n) -> Vec<i64>`
  - Factorize n, return all divisors
  - Memoize common factors (2, 3, 5, 7, etc.)
- **New method:** `valid_quotient_pairs(x_bounds, y_bounds, product) -> Vec<(i64, i64)>`
  - For each x in x_bounds, check if product/x is integer and within y_bounds
  - Return all valid (x, y) pairs
- **Update propagate():**
  - Compute valid pairs
  - Prune x domain to valid x values; prune y domain to valid y values
  - Tighten bounds accordingly
- **Tests:**
  - `multiply_bounds_forces_quotient` - bounds force a unique factorization
  - `multiply_bounds_prunes_invalid` - bounds eliminate impossible factors
  - `multiply_bounds_both_open` - both x, y open but bounds limit pairs

**Estimated LOC:** 40-50 (factorization + pair enumeration)

---

### Task 3: Element — Index/Array Bounds Propagation (MEDIUM PRIORITY)

**Ceiling:** Currently prunes only when idx or y fixed; misses bounds-based filtering.

**Upgrade:** Prune idx domain by which array indices contain values in y bounds.

**Example:**
```
y = array[idx] with array=[5,15,25], y ∈ [10,20], idx ∈ [0,2]
→ array[0] = 5 ∉ [10,20] → prune idx = 0
→ array[1] = 15 ∈ [10,20] → keep idx = 1
→ array[2] = 25 ∉ [10,20] → prune idx = 2
→ Result: idx = 1 (fixed), y = 15 (fixed)
```

**Implementation:**

- **File:** `rust/src/propagators.rs`, Element impl
- **New method:** `prune_idx_by_array_bounds(store, idx, array_indices, array_cell, y_bounds) -> Result`
  - For each possible idx value, check if array[idx] is within y bounds
  - Prune idx values whose array entries are outside y bounds
- **Update propagate():**
  - Compute y bounds from store
  - Call prune_idx_by_array_bounds
  - If idx becomes fixed, commit y to array[fixed_idx] and prune y domain
- **Tests:**
  - `element_bounds_prunes_idx` - y bounds eliminate certain indices
  - `element_bounds_fixes_y` - idx bound forces specific array entry
  - `element_bounds_both_open` - idx and y open but bounds filter index range

**Estimated LOC:** 35-45 (index enumeration + filtering)

---

### Task 4: Cardinality — Per-Value Occurrence Bounds (LOW PRIORITY, v2.3 candidate)

**Ceiling:** Currently counts fixed/open only; doesn't track which values must/cannot occur.

**Upgrade:** Compute min/max possible count per value using domain bounds.

**Example:**
```
at_least_2(x, y, z, value=3) with:
  x ∈ [1,2], y ∈ [3,4], z ∈ [5,6]
  
→ Can x = 3? No (outside domain)
→ Can y = 3? Yes (3 ∈ [3,4])
→ Can z = 3? No (outside domain)
→ Max count of value 3 = 1 (only y can be 3)
→ Constraint requires at_least_2, but max_count = 1 → Conflict
```

**Implementation:**

- **File:** `rust/src/propagators.rs`, Cardinality impl
- **New method:** `max_count_per_value(store, cells, value) -> usize`
  - For each cell, check if value is within domain bounds
  - Count cells where value is reachable
- **New method:** `min_count_per_value(store, cells, value) -> usize`
  - For each cell, check if value is the only value in domain
  - Count cells where value is forced
- **Update propagate():**
  - Compute min/max counts for the constraint's value
  - Check: `min_count <= count <= max_count`
  - If violated: return Err(Conflict)
  - If min_count == max_count == count, force all reachable cells to value
  - If no more cells can reach value, prune value from all cells
- **Tests:**
  - `cardinality_bounds_detects_infeasible` - bounds show constraint cannot be met
  - `cardinality_bounds_forces_value` - bounds force value in open cells
  - `cardinality_bounds_mixed_fixed_open` - mix of fixed and open cells

**Estimated LOC:** 30-40 (per-value reachability analysis)

## Implementation Order

1. **NeqLinear** (HIGH priority, highest N-Queens impact)
   - Diagonal constraints in N-Queens rely on NeqLinear
   - Bounds reasoning directly improves pruning

2. **Multiply** (MEDIUM priority, deferred if time-boxed)
   - Lower frequency in golden problems
   - Can defer to v2.3

3. **Element** (MEDIUM priority, deferred if time-boxed)
   - Needed for reachability/scheduling problems
   - Can defer to v2.3

4. **Cardinality** (LOW priority, v2.3 candidate)
   - Useful for counting constraints
   - Can defer to v2.3

## Known Risks & Mitigations

| Risk | Mitigation |
|------|-----------|
| Bounds/domain inconsistency | Always prune domain after tightening bounds; test both paths |
| Performance regression | Profile before/after; revert if > 2% worse |
| Overflow in interval arithmetic | Use i64; check for min/max value boundary cases |
| Missing edge cases | Existing test suite must pass 100%; add new tests for bounds-specific scenarios |
